# Work: shared tasks, views and history

Work → Tasks → Work board shows the parent tasks deliberately created through Create task in the UI or from a conversation. A parent is optional and can hold one session or many; opening a session never creates a Kanban card by itself. Child tasks, session requests and internal support records stay out of the Kanban. Needs You, Waiting For and Handoffs retain their existing activity and requests. Company and domain filters and Board/List/Timeline selection are remembered for the signed-in account. Closing a conversation does not close its parent task. Selecting a card opens the same task ID.

**Proposed lane and multi-company cards.** The board opens with a Proposed lane ahead of the hub's six outcome states. It is not a seventh hub state: a card is proposed while it carries the hub tag `proposed` and its standing is still Backlog or Ready. Moving a proposal to Backlog removes the tag; moving it further removes the tag and then runs the outcome verb with the advanced revision; any lane can be parked back to Proposed with one tag write. A card is for several companies when, besides the company the hub files it under, it carries `company:<slug>` tags (`src/shared/proposed-task.ts` holds the vocabulary). Cards show every company as a chip, the domain, and the description; the company filter matches any of a card's companies; a department is optional. Create task, the board's Propose button and the session "+" menu ("Propose an idea") write the tags on the card immediately after creation through the console's filing verb, and report a refused tag write instead of hiding it. Ideas filed from a chat through the omni-console MCP `propose_task` (or `create_task` with source `omniconsole-task` plus `update_task` tags) are shown on the board even when the hub's eligibility rule keys on another source, because the tag is the deliberate act.

Cards show the accountable owner separately from the next actor reported by the existing obligation projection, with next action, waiting reason, due/update time and reply count. Missing actors or actions are named as missing. The board reads the hub's six outcome states: Backlog, Ready, In Progress, Waiting, Review and Done. Execution conditions and session counts appear as badges. Older servers use the existing explicit parent source and task-state mappings. A failed or finished session never completes an outcome; one session waiting on a human does not put the whole parent in Waiting while other work continues. Other work and cancelled records remain available in List.

Agents maintain the existing task through the shared lifecycle actions and the current revision: start when actively pursuing it, wait with a blocker and durable wake/follow-up, resume after that blocker resolves, and submit a completed candidate for review. Canonical workflows retain their guarded claim, attempt, wait/wake and verification transitions. The task preamble is delivered to native chat, terminal launches and workflow workers; the server supplies current permissions and action requirements. Notes retain context but never change status. Done remains subject to the task's actual acceptance criteria and existing proof policy. A prerequisite approval belongs in Waiting; review of a completed candidate belongs in Review.

Create task and Attach to task read the saved parent's server-compiled context and memory after confirming the session link. The next ordinary chat or terminal-composer send includes that context once, with its task revision and provenance. Pending context belongs to the exact signed-in account, execution host and provider session; a replacement conversation cannot inherit it by reusing a pane. Retry sends preserve the original payload. Unavailable or stale context leaves the saved link intact and shows a warning to refresh the task before continuing. Direct keystrokes into a raw terminal bypass the composer and are not intercepted. Attaching a parent does not replace an existing host-bound execution contract.

Visible boards, handoff projections, task notes and lifecycle detail refresh every 30 seconds. Focus refreshes the board and obligations immediately. Refused reads remove their records and show a failure; capped feeds and unavailable company/domain names are explicit. Search and session pagination cover returned records, not an invented complete archive.

Task detail includes the shared human/AI activity trail, note entry, artifacts and SHA-256 digests, existing handoff review controls, workflow graph and typed actions, attempts, sessions and existing waits. Notes never confer approval. Handoff review binds exact version IDs and a retained operation ID; an in-flight guard prevents double clicks. Blocked prepares the current task revision and submits a reason through the existing guarded update. A stale/refused update requires refresh.

Workflow dependencies, conditions, states and readiness come from the lifecycle or workflow API. Existing human actions and local execution controls are reused. Wait source/reminder health is only displayed when reported; missing health is unknown. A missing session or unavailable log is not evidence of inactivity. Session detail links back to the canonical Work item through the existing web surface.

# OMP OpenRouter routes

A saved actor may add `openrouterCandidates`, an ordered list of 1–16 exact OpenRouter API IDs without the outer `openrouter/`. The agent is `omp`, its selected model is the full `openrouter/<first candidate>` selector, and duplicate, empty, whitespace-altered, or reordered selectors are invalid. An absent list means fixed-only execution. Do not synthesize a list when loading older drafts.

Workflow steps, graph nodes, and backend execution policy use `openrouter_candidates`. Candidate order participates in new revision and action identities only when the field is present; legacy identities stay unchanged. Preview, admission, recovered admission, and paired-host launch receipts must preserve the exact list. Older servers that strip it fail closed.

Fleet eligibility comes from current inventory rows and their explicit ready/allowed host membership for every selected candidate. The IDE does not widen the fleet model policy. Reconciliation of an already accepted request uses the backend's reconciliation proof, not fresh inventory, and still checks the saved route echo.

Execution-host discovery annotates eligible model rows with `openrouterRouting: "omp-openrouter-routing-v1"`. Only the execution host adds this marker after its authenticated OMP model probe, OMP 18.2+ version check, and exact OpenRouter public tools-capability check. Static catalog membership is insufficient. Main rechecks before admission and launch. Paired runtimes negotiate `omp-openrouter-routing-v1`; local task continuation additionally requires the backend `task_continuation.openrouter_routing` capability. Plain SSH uses the additive `agent.ompRouteDiscoverV1` and `agent.ompRoutePrepareV1` relay methods, whose replies must attest `omp-openrouter-routing-v1`. Older relays return an explicit capability refusal; WSL, Windows SSH, and custom launchers remain unsupported for exact routes.

Local launch writes a content-addressed, routing-only config in the existing user's OmniConsole home. Fixed selection disables both model fallback and usage-aware fallback. An explicit list enables OMP's native `retry.modelFallback` and ordered `retry.fallbackChains`, with `fallbackRevertPolicy: "never"`, in one process and session. It never retries the workflow or completed tools. Unknown user configs cannot override a saved route; managed configs can be reused on resume. Credentials remain in the existing environment and provider home.

A successful canonical local result includes observed OpenRouter provider/model attempts from the exact process-bound OMP session transcript. A fresh session header and successful terminal assistant result are required; requested values alone are not execution evidence. Missing, stale, changing, or out-of-route evidence blocks successful publication. Physical process exit is still independently verified by the existing execution-host receipt.

Canonical reviewer loops currently refuse per-seat fallback lists because the backend loop contract cannot represent them losslessly. Fixed reviewer models retain their individual selectors. Enabling reviewer fallback requires an additive backend contract and exact per-seat preview/receipt validation first.

Plain SSH route preparation rechecks every candidate against the host-authenticated catalog before writing the same immutable config under the host home. The request carries exact identities, order, and approval intent only: no client path, credential, or environment is accepted. Permission switches are allowlisted; unknown config/launcher arguments fail closed. Startup, PTY Chat, resume, worker dispatch, and outcome launch reuse the prepared host argv; SSH resume uses the provider session ID. Shell functions cannot replace the selected OMP command. Fleet membership and backend allowlists are unchanged.

Switchable PTY Chat and its work rail resolve OMP transcript IDs through the relay's existing host session index, then read the host's bounded tail decoder via `transcript.readOmpTailV1`. The reply must attest `omp-transcript-tail-v1` and the exact agent/session. Reads are fenced to the SSH provider generation; missing capability, owner changes, and unresolved owners never fall back to client files. Old clients ignore the new method; new clients see an explicit refusal from old relays. No paired-runtime registration or remote ACP session is required; Grok/Pi local-only restrictions remain unchanged.

Signed ordinary-SSH acceptance must use a normal SSH folder/worktree and the existing host account on an allowed fleet machine. On the integrated signed build, exercise a fixed route and an ordered fallback route in Terminal and PTY Chat, switch views without spawning a second process, then resume and dispatch/continue with the saved route. Collect the remote argv/config hash, execution-host/session identity, fresh successful transcript, observed model attempts and effective model, and host acknowledgement for any stop. Also exercise an old-relay or unsupported-version refusal. Discovery, unit fixtures, and paired-host tunnels are not execution evidence.

# TypeSafe capability roadmap and measurement contract

Prepared 2026-09-20 for the implementation in this branch. This is a source-level capability and measurement map, not a claim that all capabilities have been exercised in production. Attach dated experiment receipts and required GitHub check results separately. No test suite was run to prepare this document.

TypeSafe is most promising here for small, explicit classifications that would otherwise require a generative-model call or manual report triage. The integration supports useful advisory output now. Its orchestration observers deliberately receive too little substantive evidence to replace reviewers, choose the best implementation, approve tools, or establish completion.

Shadow evaluation adds inference cost and processing overhead while the existing decision still runs. It does not save that decision's cost. No finite experiment can prove 100% correctness, and confidence 1.0 does not establish certainty. Existing authority, receipt validation, execution-host ownership, GitHub requirements, and human acceptance remain the governing mechanisms.

These are concrete properties of the TypeSafe API, not a claim that no other system can provide typed classification. Choice supports up to 255 options. Score is the probability-weighted mean of zero-based rubric levels. Noul is a yes probability rather than a severity scale. See [Choice](https://docs.typesafe.ai/primitives/choice), [Score](https://docs.typesafe.ai/primitives/score), and [Noul](https://docs.typesafe.ai/primitives/noul).

Questions in the same request are independent; their IDs are response keys, not instructions seen by the model. Each question therefore needs a complete instruction naming the relevant state. A later answer that depends on an earlier answer requires a separate stage. Provider examples of batching gains are not measurements of this application. See [Primitives and batching](https://docs.typesafe.ai/primitives).

Confidence is derived from the returned distribution. The exact formula is not specified on the referenced page, and a threshold has to be calibrated against the actual workload. See [Confidence](https://docs.typesafe.ai/confidence).

The provider documents weaknesses in arithmetic, counting, time comparison, indirection, and adversarial content. Keep exact accounting, time windows, receipt checks, permission checks, and arithmetic in code. Adding more irrelevant context can reduce quality. No probabilistic answer grants permission to act. See [Jev 1.13 limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

## Orchestration: all nine capabilities

Every row below is shadow-only in the decision service, regardless of a profile asking for live mode. The main hook runs after `SessionOutcomeService.save()` successfully flushes authoritative state. Tool observations subscribe to normalized agent-hook events. The observer receives copied counts and flags, hashed references, and no runtime or mutation callback. The existing answer travels separately as comparison metadata and is excluded from inference state.

Nine event categories do not mean nine semantic evaluations are complete. The four verdict categories do not inspect the candidate, routing reconstructs a recorded route, handoff summarizes delivery, Done When approximates structural proof presence, tool action categorizes known names, and error classification omits diagnostics. Measurement improvements below make these limited comparisons auditable; they do not establish semantic review, artifact verification, improved quality, or saved cost.

The denominator described here is the desired logical unit. Current retained telemetry does not reliably count every eligible unit; the gaps below must be addressed before a coverage claim.

Projection work on the authoritative save path is explicitly bounded: a shared budget inspects at most 512 source-array entries per save, with at most 32 entries from the tail of any array. Review-loop traversal is further limited to the latest four groups, two rounds per group, and eight receipts per round. At most 32 observations per save and 64 pending observer deliveries are admitted; a full delivery queue skips source inspection. Identifiers are length-limited before comparison, normalization or hashing. No full history is serialized, and only newly created scalar projections—not mutable chains or receipt objects—reach the detached observer.

These limits are deliberate sampling, not exhaustive lifecycle coverage. Earlier entries and ambiguous unmatched prior records can be omitted, and one busy category can consume the shared budget before another category is sampled. Array lengths remain exact, but derived proof, active-attempt and delivery counts are `null` when their required population is incomplete, with explicit completeness flags. Missing is not zero. This bounds work independently of retained history size; it does not establish zero latency or measured production overhead. Disabled decision-service configuration still permits this bounded projection when the runtime observer is installed, but cannot initiate provider inference.

### Denominator traps

- The same review decision can first appear in review-loop state and later as a chain verdict during separate saves. Within-save deduplication does not prove cross-save uniqueness. Count event records until stable decision identity and deduplication are implemented; do not label the raw count “reviews evaluated.”
- Tool pre/post/failure hooks are multiple events, not necessarily separate invocations. Some providers do not expose a stable tool invocation ID. Report events and uniquely identified invocations separately; leave the latter unknown when identity is unavailable.
- Initial state without a prior chain is intentionally not replayed into the observer. Skipped verdict receipts and unchanged projections are excluded. Disabled observers, malformed projections and pre-service queue limits can omit events without decision-service telemetry.
- Tail windows, the shared source-read budget, oversized identifiers and ambiguous prior samples cause additional pre-service omissions. Runtime counters now expose those stages, but sampled-out array entries and skipped hook calls are not counts of eligible decisions. No dropped-event counter reconstructs that unknown population. Truncated handoff projections can have an `unknown` comparison when there is no authoritative delivered status or explicit exception; exclude those from authoritative-baseline agreement denominators.
- Unknown and insufficient-evidence responses are valid abstentions. Report them separately; do not silently count them as either correct decisions or provider failures.
- Agreement is not independent accuracy. A correct abstention can disagree with an authoritative verdict whose substantive evidence was intentionally withheld from the shadow model.

Automatic completed-run observation currently examines a bounded recent population, so “all routines” is not a valid denominator.

## Evidence required before claiming improvement

Separate four claims: the API works; the classification matches independent labels; replacing an existing operation improves latency/cost; and the changed workflow improves user/business outcomes. One does not prove the next.

1. Pin the application commit, resolved model ID, projection/question version, evidence scope and a dated sample definition. Define which units are eligible and which are excluded before reading the results.
2. Use representative, independently labelled examples, including ambiguous, missing-evidence, stale, contradictory and adverse cases. Keep tuning cases separate from held-out evaluation. Ordinary operational observations and existing required GitHub checks are the allowed verification channels; this roadmap does not authorize additional local/fleet test sweeps.
3. Record all selected cases: successes, abstentions, failures, skips and drops. Distinguish labelled fixtures from naturally occurring production events. A provider/API fixture demonstrates integration on that fixture; it must not be reported as live lifecycle traffic.
4. Compare the same input/evidence revision with the existing method. Keep the original answer out of model state. For workflow cost/speed claims, instrument both paths and identify exactly which old work would stop running.
5. Report sample count, time window, p50/p95 decision latency, failure rate, coverage, independent error rates and uncertainty. Stratify by capability, evidence scope, model, host and transition type. Correlated repeats from one run do not create independent evidence.
6. Propose promotion for one narrow use case with an explicit acceptable-error limit, minimum useful coverage and measured benefit. Critical false-pass or unauthorized-action outcomes are distinct from harmless display errors. Promotion is an authorized implementation change, not a confidence threshold silently granting broader authority.

No universal sample size establishes safety. As an illustration, zero failures across 300 independent representative cases still leaves an approximately 1% one-sided 95% upper bound on the failure rate; around 3,000 such cases gives approximately 0.1%. These are statistical illustrations, not acceptance requirements, and cease to justify those bounds when sampling assumptions fail.

## Current measurements versus missing evidence

For the controlled orchestration `classification` question, telemetry now includes the allowlisted `baselineValue` and validated choice `probabilities`, alongside measurement metadata: `baselineSource`, `evidenceScope: structural_metadata`, and `projectionVersion: orchestration-structural-v2`. New distribution/baseline fields are restricted to the fixed lifecycle vocabulary, not arbitrary question labels or candidate IDs. No baseline answer, telemetry context, prompt, diagnostic, artifact, or transcript is added to provider state by this change.

`measurement.eventReference` hashes the bounded source reference; `measurement.eventFingerprint` hashes its capability, projection version, hashed reference and newly created count/flag projection. These support joins when the authorized caller holds the corresponding source reference and projection. Neither includes plaintext source identifiers or private content. Identical repeated projections share a fingerprint, and a review-round receipt and later chain receipt can have different references: these hashes are not unique occurrence IDs or automatic deduplication.

Runtime status exposes `measurement.service` counters since that decision-service instance was created and `measurement.observer` counters since process start. Service counters cover admission, enqueue, start, terminal completion/cancellation, invalid/disposed/full/cleared-queue drops, ring eviction and append-sink outcomes. Observer counters cover observed calls, missing baseline/filtering, source sampling, ambiguous baseline and oversized-field omissions, projected observations, per-save/queue drops, queued/started/suppressed deliveries and callback failures. They are fixed-size saturating counters, runtime-only and not durable or per-capability historical ledgers. `sourceEntriesOmitted` counts entries in sampled arrays, potentially including the same history again on a later save; it is not missing-event count. `queueFullCalls` counts hooks or saves skipped without inspecting their source. `oversizedIdentitySkipped` counts field checks, not unique records.

An append callback resolving is not proof of durable persistence: the installed sink deliberately returns without writing during its one-second throttle. Failed/overflowed appends and ring evictions are separately counted, but counters disappear on process/service restart and do not establish a complete observation denominator. Counters at different stages overlap and must not be summed into a single failure or eligibility total.

The installed runtime telemetry ring retains 256 events; the generic telemetry class defaults to 128 and permits up to 512. The private record retains its existing 512 KiB file limit. Runtime snapshot persistence is throttled to at most once per second, so events after the last persisted snapshot can be lost. An optional append sink can also fail or overflow without blocking execution. Runtime counters expose invalid requests, cleared work and many pre-service omission stages, but they do not create missing event records or survive restart. A recent telemetry snapshot is therefore not an exhaustive experiment ledger.

The next narrow semantic experiment could compare admitted raw provider failure reasons with the existing three-way `classifyAgentTurnFailure` classifier. ## Implementation sequence

1. Finish the current typed routine recommendation/classification flows, provider failure handling, authenticated action preview/readback and required GitHub acceptance. Exercise only authorized operations and label fixtures as fixtures.
2. Extend the bounded measurement metadata and runtime stage counters into a separately authorized durable experiment ledger with stable logical-unit/occurrence identities, independent labels and paired timings. Keep absent baselines explicitly unknown; the current structural baseline and distribution fields alone do not prove quality.
3. Collect representative advisory-report and advertising-recommendation evidence. Tune narrowly against held-out labels; measure human usefulness as well as model agreement.
4. Explore Score for semantic severity and Noul for a single report-evidence predicate where exact code cannot answer the question. Batch independent questions and enforce combined policy in code.
5. Consider narrowly scoped semantic routing or error triage only after evidence improves on existing exact metadata. Review, judge, adversarial review and verification need substantive immutable evidence before replacement experiments make sense.
6. Keep receipt checks, handoff identity/delivery, permission enforcement, budget authority and Done When completion mechanical. A model may advise on ambiguous evidence; no measured gain here justifies giving it those authorities.
